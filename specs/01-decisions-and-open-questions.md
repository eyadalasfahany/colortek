# 01 — Decisions and Open Questions

This is the register. When anything is unclear anywhere else in the spec set,
the answer is here or it does not exist yet.

## Part A — Confirmed decisions

Each row was decided by the client in the requirements session. Do not change
any of these without asking.

### Scope and platform

| # | Decision |
|---|---|
| A1 | Phase 1 = workflow engine, tasks, timers, samples and formula traceability, site visit and readiness. |
| A2 | No cost model, no material engine, no AI, no delivery workflow in Phase 1. |
| A3 | Backend: Laravel + MySQL. Frontend: Next.js. One environment. |
| A4 | Permissions use `spatie/laravel-permission`, fine grained from day one. |
| A4b | Roles and permissions are managed by a **super admin** through a screen: create a role, choose its permissions, assign roles to users. Nothing about roles is hardcoded. |
| A5 | No real Odoo integration in Phase 1. Build on seeded data behind a gateway so the integration can be added later without rewriting business logic. Odoo integration happens after the system is accepted. |

### Projects

| # | Decision |
|---|---|
| A6 | Sales creates the project inside our system. |
| A7 | Stages: Lead → Quotation → Payment → Sample → Site → Production → Execution → Delivery → Completed. Sample and Site may run in parallel. |
| A8 | Record numbers derive from the Odoo quotation number. |
| A9 | A project is finished when delivery is confirmed and the final payment is received. Because Delivery is Phase 2, Phase 1 closes projects manually with a permission. |

### Tasks and people

| # | Decision |
|---|---|
| A10 | Tasks go to a **department queue**. Any member of that department claims them. No named assignment. |
| A11 | Phase 1 logins: office staff, workshop and tinting supervisors, site supervisors and project engineers. No individual worker logins. |
| A12 | Workshop time is tracked with **live start/stop timers** run by the supervisor. |
| A13 | Site time is tracked with an **end-of-day crew log** per project per day. |
| A14 | Working calendar: Friday weekend, one fixed daily shift, official holidays. Deadline clocks pause outside working hours. |
| A14b | The shift is **09:00 to 17:00**. |
| A14c | Holidays are **not a fixed seeded list**. An admin adds, edits and removes them through a screen in the system. |
| A15 | Deadlines come from a default per task type, can be overridden per project, and can be overridden per task by a user with permission. |
| A16 | Blocker categories: Site not ready, Missing material or product, Waiting for the client, Technical problem or missing information. |

### Payments

| # | Decision |
|---|---|
| A17 | Every installment runs the full cycle: Sales confirm → Reception review → Daily Journal → Accounting. |
| A18 | A late or missing payment never blocks operational work. It is informational only. |
| A19 | Payment proof file is **mandatory**. Sales cannot complete the payment task without it. |
| A20 | One Daily Journal per day for the whole company. |

### Samples and formula

| # | Decision |
|---|---|
| A21 | Samples may exist before a sale. A sample requires a client; the project link is optional and can be attached later. |
| A22 | Manager approval is **always** required for a sample request, performed by one fixed Approver role. |
| A23 | Client approval is a **printed PDF form** generated by the system, signed by the client, scanned and uploaded. No client portal. |
| A24 | A modification request creates a **new sample linked to the previous one**, never an edit of the old sample. |
| A25 | A formula is a free-text note or a scanned photo of the tinting sheet, versioned, with author and date. Not structured lines in Phase 1. |
| A26 | Formula content is visible to anyone who can see the project. No field-level secrecy. |
| A27 | Tinting authors the formula. Reception registers it in the system. Both identities are stored separately. |

### Site

| # | Decision |
|---|---|
| A28 | The digital site visit report must reproduce the existing paper form field for field. The real form has been supplied (`docs/`) and is transcribed in `07-workflows/05-site-visit-and-readiness.md`. |
| A28b | The report has two parts: a **measurement sheet** (building elements with length/width/thickness/diameter and inline deductions, 23 rows per page, multi-page) and a **site condition statement** (humidity + 3 yes/no checks + overall readiness). Both parts are signed by the client and the project engineer. |
| A29 | When a site is Not Ready, **only work performed at the site is blocked**. Workshop preparation continues. |
| A30 | A company setting can switch A29 to "block everything for this project". |
| A31 | Overriding a site block is controlled by its own permission. The person must write a reason, which is saved to the audit log. |

### Interface

| # | Decision |
|---|---|
| A32 | Arabic and English, switchable by the user, with full RTL layout. Designed in from the start, not retrofitted. |
| A33 | Notifications in Phase 1 are in-app only: a badge and a notification centre. No email, no WhatsApp. |

### Delivery (defined, but built in Phase 2)

| # | Decision |
|---|---|
| A34 | Delivery is **two separate stages**: (1) material delivery from workshop to site, (2) final handover of finished work to the client. Different owners, different documents. |

## Part B — Proposed by us, open to correction

These are our decisions, not the client's. Each one is safe to reverse.

| # | Proposal | Why |
|---|---|---|
| B1 | Record numbers derive from the Odoo sales-order / quotation number, confirmed by the supplied forms as `SO9577`. So: project `SO9577` → sample `SO9577-S1` → formula `SO9577-S1-F1` → site visit `SO9577-SV1` → task `SO9577-T012`. | The client said numbers come from the quotation number; the real form shows the format. |
| B2 | A sample chain (original + all modification descendants) is shown in the UI as one thread with a counter, so "this took 3 attempts" is still visible even though each attempt is a separate record. | Preserves the reporting value the client wanted without changing the record model they chose. |
| B3 | `Overdue` is a computed flag, not a task status. A task can be In Progress **and** overdue. | The vision document listed it as a status, which would lose the real status. |
| B4 | Task statuses: `pending`, `ready`, `claimed`, `in_progress`, `paused`, `waiting`, `blocked`, `completed`, `cancelled`. | See `06-task-and-time-tracking.md`. |
| B5 | Workflow templates are versioned. Editing a template creates a new version. Running instances keep the version they started on. | Otherwise editing a template corrupts live work. |
| B6 | Attachments are stored on local disk in Phase 1 via Laravel's filesystem abstraction, so switching to S3 later is a config change. | Single environment, no cloud storage decided. |
| B7 | API authentication uses Laravel Sanctum tokens. | Standard for a Laravel + Next.js pair. |
| B8 | Activity events and audit log are two separate tables with different purposes. Activity is the human feed; audit is the legal record. | They have different retention and different readers. |
| B9 | A user may hold more than one role, and may belong to more than one department. | Small company; people wear several hats. |
| B10 | One user may have only **one running timer at a time** across the whole system. Starting a second one pauses the first and records why. | Prevents double-counted hours. |

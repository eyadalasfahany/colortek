# 11 — Audit Trail and Exception Handling

---

## 1. Audit versus activity

The activity feed is prose for humans. The audit log stores **values**, and
exists to answer "who changed this, from what, to what, and why" months later.
`[PROPOSED]` B8

They are separate tables because they have different readers, different
retention, and different tolerance for loss. Losing a feed line is annoying.
Losing an audit row is a problem.

---

## 2. What is always audited

| Area | Why |
|---|---|
| Formula created, registered, corrected | The author/registrar separation is meaningless if the record can be quietly rewritten. `[CONFIRMED]` A27 |
| Sample approvals, manager and client | The client decision is a commercial commitment |
| Payment records and proof files | Money |
| Journal submission, reopening | Accounting record |
| Task reassignment and forced release | Accountability for who was responsible |
| Deadline overrides | Otherwise every SLA report is meaningless |
| Site readiness decisions | Decides whether work is blocked |
| Every override (all three kinds) | See §4 |
| Time entry corrections | Hours become cost in Phase 2 |
| Project completion and cancellation | |
| Role and permission changes | |
| Workflow template publishing | Changes how work is created |
| Settings changes | Shift hours change every deadline in the system |

Each row stores: the record, the event, the user, old values, new values, the
reason when one is required, the IP address, and the time.

Retention `[TBD]` D13 — the company's accounting obligations decide it. Until
answered, nothing is deleted.

---

## 3. Rules

1. **Audit rows are written inside the same transaction as the change.** If the
   change is rolled back, so is the audit row. If the audit write fails, the
   change fails. An unaudited change to an audited area must be impossible.
2. **Nothing is ever updated or deleted from `audit_logs`.**
3. **The reason field is not optional where it is required.** The API rejects the
   request; it does not save with an empty reason.
4. Only `audit.view` can read it. Reading the audit log is not itself audited in
   Phase 1.

## 4. Overrides

Three exist in Phase 1. `04-permissions-and-roles.md` §5.

| Override | Permission | Effect |
|---|---|---|
| Start site work while the site is not ready | `site.override_block` | One specific task released |
| Complete a payment task without proof | `payment.skip_proof` | Granted to nobody by default |
| Reopen a submitted journal | `journal.reopen` | |

Every override: requires the permission, requires a typed reason, writes an audit
row with `event = 'override'`, and produces a `warning` activity event visible to
management.

The system never silently allows an exception. It allows it loudly. That is what
makes it safe to allow exceptions at all — and a system that allows none gets
worked around outside the system, which is worse.

## 5. Exceptions the system must handle

The vision document's section 62 lists these. Each needs a defined behaviour, not
a stack trace.

| Situation | Behaviour |
|---|---|
| Payment proof missing | Completion refused, naming the missing file. Only `payment.skip_proof` can pass |
| Quotation cannot be locked | Sales cannot complete; they block the task with a reason instead |
| Assigned person is absent | Not applicable — tasks belong to departments. `[CONFIRMED]` A10. A claimed task can be force-released with `task.reassign` |
| Workshop cannot proceed | Block the task with a category and reason |
| Sample reference missing | The reference is generated by the system, never typed. Cannot happen |
| Formula incomplete | Cannot be saved without either text or a scanned sheet |
| Site inspection fails | The defined not-ready flow, not an error |
| Material unavailable | Block with `missing_material`, which notifies the warehouse. Phase 1 has no purchase request; that is Phase 2 |
| Timer left running | `CloseStaleTimers` stops it at shift end and flags it for review. `06-task-and-time-tracking.md` §5.1 |
| Two people claim the same task | Atomic claim; the loser gets a plain "Ahmed took this task" |
| A task is completed twice | Idempotency key returns the first result. `08-api-contract.md` §1 |
| Duplicate task creation | A partial unique index prevents two open tasks for the same instance and definition. `05-workflow-engine.md` §6 |
| A cancelled task was the only path forward | The instance appears on the stalled-instances admin screen. `02-architecture.md` §9 |
| A workflow template is edited mid-flow | Running instances keep their version. `[PROPOSED]` B5 |
| Crash during task completion | The whole completion is one transaction. `05-workflow-engine.md` §1 |
| Odoo unreachable | Phase 2. The push is queued and retried; work never stops |
| The upload fails on a phone | Files are uploaded separately and referenced by id, so a filled form is never lost. `08-api-contract.md` §12 |
| The engineer loses signal on site | The whole form is a local draft. `09-screens/05` |

## 6. Failures that must be visible

A workflow engine can fail silently, and a silent failure looks exactly like
"nobody has done it yet". Three admin screens exist for that reason:

1. **Stalled instances** — running instances with no open task.
2. **Unclaimed queues** — tasks sitting in `ready` past their SLA with nobody
   claiming them. This catches a department queue nobody is watching, which is
   the most likely real failure of this system in its first month.
3. **Failed jobs** — with the error, and a retry button.

Each is a list, not an alert email. Someone has to look, and the admin screen is
where they look. `[PROPOSED]` — if these three lists are never checked, add a
daily digest in Phase 2 when email exists.
